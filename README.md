# 云端助手 ⇄ 本机执行端：AI 任务中转协议

> 让"云端大模型"和"本地电脑"安全协作的一套轻量协议：任务卡 + 回执 + 状态机，纯文件系统实现，不需要服务端、不开端口。

## 它解决什么问题

云端 AI 能思考、能拆解，但碰不到你的电脑；本地脚本能操作电脑，但不会做复杂判断。
把一件复杂任务拆成 **谁决定 / 谁执行 / 谁验收** 三段，中间用文件交接，就能既让 AI 干活，又把权限卡死。

这个仓库沉淀的是这套交接协议的**设计方法与可复用骨架**，不含任何真实业务数据。

## 核心设计

| 机制 | 做法 | 为什么 |
|---|---|---|
| 三目录交接 | `outbox/` 派发 · `inbox/` 回执 · `archive/` 归档 | 单向写入，谁写哪个目录是硬约定，避免互相覆盖 |
| 状态机 | 待认领 → 已认领 → 已完成 / 失败 / 需人工批准 | 状态写在单一文件里，人和 AI 读同一份真相 |
| 认领幂等 | 任务卡文件名即主键，认领时先改状态再动手 | 防止同一任务被并发重复执行 |
| 操作红线 | 涉及钱、对外发布、删除、改系统设置的，一律停手，回执写"需人工批准" | 权限用白名单表达，不靠模型自觉 |
| 失败上限 | 同一任务最多重试 1 次，再失败就停止并回报 | 避免死循环烧时间和额度 |
| 证据留痕 | 每条回执必须附证据路径（文件/截图），没有证据视为未完成 | 可回溯，便于验收 |

## 目录结构

```
outbox/     任务卡：待执行的任务，按编号命名
inbox/      回执：执行结果 + 证据路径，与任务同号
archive/    归档：验收完成的任务卡与回执
protocol/   模板：任务卡与回执的字段定义
docs/       设计说明与角色分工
STATUS.md   一行一任务的全局状态表
```

## 关键取舍

**为什么用文件而不是 HTTP API？**
本地端不需要开端口、不需要暴露到公网；git 历史本身就是审计日志；断线后状态不丢，重放即可续跑。
代价是实时性差，适合"分钟级"任务，不适合流式交互。

**为什么红线要写在任务卡里，而不是写在模型提示词里？**
提示词会被上下文挤掉，任务卡不会。每一单都重新声明一次允许范围，比指望模型一直记得更可靠。

**为什么区分"失败"和"需确认"？**
"失败"可以重试，"需确认"重试一万次也还是那个结果。混淆这两者会让自动化看起来在跑，实际卡死。
