# 设计说明

## 1. 状态机

```
待认领 ──认领──▶ 已认领 ──执行成功──▶ 已完成 ──验收──▶ 归档
                    │
                    ├──执行失败──▶ 失败（最多重试 1 次）
                    └──越界/信息不足──▶ 需人工批准（不重试）
```

状态只写在 `STATUS.md`，一行一个任务。人和 AI 读同一份文件，避免"我以为它做了、它以为我批了"。

## 2. 幂等与并发

任务卡文件名就是主键：`T0001-简短名.md`。
认领的原子操作是"先改状态、再开始干活"，而不是"先干活、后改状态"——反了就可能在改状态前崩溃，留下一个没人认领却被执行过的任务。

由于现实中只有一个执行端，这里不引入锁服务，用"文件名 + 状态"就够了。

## 3. 权限边界

每个任务卡都必须显式列出**允许的操作**与**禁止的操作**。这是白名单式约束，不是黑名单。

默认禁止清单（任何任务都不越过的底线）：

- 付款、转账、下单一类涉及钱的操作
- 对外发布内容、发送消息
- 删除文件或数据
- 修改系统设置、账号设置
- 上传或外发任何个人证件、密钥、账号密码

越界时执行端不猜、不做，回执写 `需人工批准` 并说明卡在哪一步。

## 4. 失败语义

| 结果 | 含义 | 是否重试 |
|---|---|---|
| 已完成 | 目标达成，有证据 | 否 |
| 失败 | 环境问题、脚本报错、页面改版 | 是，最多 1 次 |
| 需确认 | 任务卡描述不清、存在多种合理解读 | 否，回报后等指令 |
| 需人工批准 | 触达红线 | 否，等人工操作 |

**关键点**：`需确认` 和 `需人工批准` 永远不该被自动重试。重试只会产生更多重复的失败回执，掩盖真正的问题。

## 5. 证据要求

回执里必须写清楚：

- 做了什么（逐条对应任务卡步骤）
- 证据在哪（文件路径、截图编号）
- 哪些步骤没做、为什么

没有证据的"已完成"一律按未完成处理。这条规则看着烦，但它把"看起来做完了"和"真的做完了"分开了。

## 6. 与模型上下文的关系

任务卡是**每一单重新声明一次**的，不依赖模型记住历史。
原因：上下文会被压缩，历史会丢；而任务卡是文件，永远在。

这也是为什么红线要写进任务卡正文，而不是只写在系统提示词里。

## 7. 已知局限

- 只支持"分钟级"任务，不支持流式、实时交互
- 单个执行端，没有分布式调度
- 状态靠人工/脚本维护 `STATUS.md`，没有强制事务
- 不做权限的密码学验证，红线靠执行端自觉遵守

这些局限是刻意的：引入服务端、队列、鉴权之后，系统的复杂度会远超它解决的问题。
